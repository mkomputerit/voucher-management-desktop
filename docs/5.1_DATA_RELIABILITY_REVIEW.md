# 5.1 Data reliability review

Review branch: `feature/5.1-reporting-core`

This document freezes the engineering study that must precede any further
behavioral change in 5.1. It is intentionally a design/review document: it does
not authorize release and it does not replace regression tests.

## Non-negotiable principles

### 1. No regressions

Behavior that is already correct must be preserved. A refactor is acceptable
only when characterization/regression tests freeze the existing correct
behavior first.

Areas currently treated as protected unless a failing requirement proves a
change is necessary include:

- official UniFi API adapter, pagination and typed errors;
- Site UUID controller identity and TLS certificate pinning;
- non-idempotent create guards and recovery;
- physical print crash boundary and HMAC audit;
- backup/restore integrity and rollback;
- ordinary deletion vs security revocation separation;
- direct UUID verification before accepting an external disappearance;
- Home live/controller-only semantics;
- shared Windows deployment and ACL model.

### 2. Reliability beyond UniFi, never invented facts

Voucher Management must preserve and make useful the facts that UniFi does not
keep available forever, especially after vouchers disappear from the live
controller. It must not fill gaps by guessing.

Positive verified facts are monotonic:

- once printed, never becomes unprinted;
- once used, never becomes never-used;
- a cumulative use count never decreases;
- first-use evidence is never erased by a later incomplete snapshot;
- once expired is positively known, it never becomes not-expired;
- deletion/revocation does not erase the local historical record.

Unknown remains unknown until there is positive evidence or an explicit
operator-owned local classification.

## Confirmed UniFi contract already present in the project

The repository's own `docs/UNIFI_OFFICIAL_API_ANALYSIS.md` records controlled
validation against Network 10.6.106.

The voucher detail contract already used by the production adapter contains:

- `id`;
- `createdAt`;
- `name`;
- `code`;
- `authorizedGuestLimit` (optional);
- `authorizedGuestCount`;
- `activatedAt` (optional);
- `expiresAt` (optional);
- `expired`;
- `timeLimitMinutes`;
- optional data/rate limits.

Project semantics fixed by requirements:

- `authorizedGuestCount` is the cumulative use count;
- `activatedAt` is the certain first-use/activation timestamp;
- validity starts from first activation, not creation;
- an expired voucher has been used;
- vouchers can disappear from UniFi after expiry, while the local archive must
  remain complete.

There is no verified `lastUsedAt` field in the voucher contract currently
consumed by the application. `last_seen_at` and `last_synced_at` are
technical synchronization timestamps and must never be presented as a last-use
timestamp.

## Current source-of-truth split

Today the application can derive one voucher from multiple partially independent
sources:

1. live UniFi `ApiVoucher`;
2. SQLite `vouchers`;
3. SQLite `voucher_prints` / `print_jobs`;
4. HMAC `history.jsonl`;
5. SQLite `legacy_audit_events`;
6. operator local metadata and `voucher_events`.

The split is legitimate as evidence storage, but user-facing modules currently
interpret it independently. That is the root cause of contradictory screens.

## Confirmed inconsistencies in current HEAD

### A. Legacy print visible in Voucher but missing from reports/alignment/revocation

The Voucher table reads `HistoryService.stats_for_codes()` directly, therefore
it can display a certain legacy print date from `history.jsonl`.

Reporting, alignment and security-revocation instead read
`voucher_prints` / `print_state` from SQLite.

The legacy migration code is capable of materializing a resolved HMAC print into
`print_jobs`, `voucher_prints` and `print_state='PRINTED'`, but that
materialization is currently an explicit maintenance path. Therefore normal
operation can continue while presentation paths disagree.

This is not a rendering problem: it is a data-lineage problem.

### B. Controller-discovered alignment contradicts the newly fixed requirement

Current `alignment.py` forces a controller-origin voucher without verified
print evidence to remain `UNKNOWN`.

The fixed product rule is now:

- verified positive print evidence -> `PRINTED`;
- PDF generation only -> not a physical print;
- controller-discovered voucher with no positive print evidence -> after
  operator alignment it is `NOT_PRINTED`.

The code, changelog and PR description must all be changed together; changing
only the dialog would reintroduce inconsistency.

### C. Legacy backup import invents expiry

`legacy_backup_import.py` creates synthetic historical vouchers with
`expired=1` even when the backup does not contain positive expiry evidence.

Existing tests currently assert this behavior.

This creates an impossible business combination such as:

- expired = true;
- usage not observed;
- ever_used = false.

It also pollutes the Expired report with rows that are merely historical, not
proven expired.

This violates the second non-negotiable principle and requires a data repair
migration for already-imported rows.

### D. Report label/data mismatch

The detailed report header says “Ultima osservazione controller”, but the
renderer currently outputs `last_synced_at`, not `last_seen_at`.

Both are technical fields and belong in full audit, but if shown there they must
be correctly named:

- `last_seen_at`: last successful snapshot in which that voucher was actually
  present;
- `last_synced_at`: last synchronization in which the local row was evaluated
  or updated;
- controller `last_successful_sync_at`: freshness of the controller snapshot.

### E. Manager-useful UniFi fields are stored but omitted by the report model

SQLite already stores `duration_minutes`, `authorized_guest_limit`,
`authorized_guest_count`, `activated_at`, `expires_at`.

The generic `ReportRow` currently omits at least duration, guest limit and
first-use timestamp, while exposing many technical fields. This is the inverse
of the desired owner/reporting model.

### F. Cumulative/positive controller facts are not fully protected against
regression

`upsert_voucher()` preserves `ever_used`, but currently overwrites
`authorized_guest_count`, `activated_at`, `expires_at` and `expired`
with every successful snapshot.

Even if normal UniFi behavior should not regress these fields, the local
archive's job is to preserve positive evidence. The persistence boundary must
enforce the domain invariants instead of relying on every future snapshot being
perfect.

## Canonical fact model

All user-facing consumers must read the same canonical voucher facts. Evidence
may still live in multiple tables/files, but one deterministic layer owns the
interpretation.

Minimum canonical facts:

### Identity / controller-owned

- controller/site identity;
- UniFi voucher UUID;
- code;
- recipient/name;
- created_at;
- duration_minutes;
- authorized_guest_limit;
- cumulative authorized_guest_count;
- first_used_at (`activatedAt`);
- expires_at;
- expired status/evidence;
- present_on_controller.

### Local/operator-owned

- nominality;
- local notes;
- origin/provenance classification;
- alignment completion.

### Print facts

- PRINTED / NOT_PRINTED / UNKNOWN;
- first verified print;
- last verified print;
- physical copies;
- reprints;
- print operators;
- evidence source when needed by audit.

A verified print from 5.x SQLite and a uniquely verified legacy HMAC print are
equivalent positive physical-print evidence.

### Deletion/revocation facts

- deletion/revocation date;
- workflow/source;
- mandatory operator reason when Voucher Management performed the ordinary
  deletion/revocation path;
- explicit absence of a reason for externally detected deletion;
- operator identity when locally known.

## Persistence rules

The persistence boundary, not the UI, must enforce:

- use count = max(previous verified cumulative count, new verified cumulative
  count);
- used = true if any positive evidence exists: use count > 0, first-use
  timestamp present, or expired positively known;
- first-use timestamp cannot be erased by null later data;
- positive expired state cannot regress;
- positive print evidence cannot regress;
- one list omission never proves deletion;
- code/name/controller-owned fields remain read-only locally.

A dedicated “expiry evidence known” state should be considered because legacy
synthetic rows currently need to represent unknown expiry rather than false
expiry. The schema already has equivalent evidence concepts for usage
(`usage_observed`) and print state (tri-state).

## Legacy reconciliation rule

Normal operation must not have one history path using HMAC facts and another
using only SQLite.

The safe existing HMAC migration machinery already:

- validates the history key fingerprint;
- recomputes HMAC only from independently known candidate codes;
- resolves only unique matches;
- preserves ambiguous/unresolved rows;
- materializes resolved prints idempotently into SQLite.

The remaining architectural decision is how this reconciliation becomes a
normal upgrade/runtime guarantee rather than a hidden maintenance prerequisite.
Until this is fixed, report/alignment/revocation consistency cannot be claimed.

## Report architecture

There must not be one universal wide table for every report.

### Manager/operator reports

Each report answers one concrete business question and contains only the fields
needed for that question.

Examples:

- Expired: recipient, creation, first use, cumulative uses/quota, first/last
  print, copies, duration, expiry;
- Used: recipient, creation, first use, cumulative uses/quota, expiry and useful
  print facts;
- Printed but unused: recipient, creation, first/last print, copies, age since
  last print, current live presence;
- Created but never printed: recipient, creation, age, nominality, live
  presence;
- Security review: recipient, last print, elapsed days, threshold, cumulative
  uses=0, live presence;
- Deleted: recipient, deletion date, deletion workflow/source, deletion reason
  prominently when known, relevant use/print state, operator when known;
- Nominality reports: recipient/classification plus the lifecycle fields useful
  to the responsible person.

Windows usernames, technical origin, UUIDs and synchronization timestamps are
not globally included just because they exist; they appear only when relevant
to that specific report.

### Full audit

Full audit is the technical reconstruction view and may contain:

- UniFi UUID;
- controller identity;
- origin/provenance;
- import/acquisition timestamps;
- last seen / last synced;
- technical event source;
- print-job/operator detail;
- deletion source;
- migration/reconciliation evidence.

## Report category review

Current report kinds mix business reports and technical diagnostic reports.

Business/manager-facing candidates include:

- summary;
- used;
- expired;
- printed;
- printed-unused;
- never-printed;
- nominal/non-nominal;
- security-revoked;
- deleted;
- threshold reviews.

Diagnostic/audit-oriented kinds include at least:

- print unknown;
- usage unknown;
- origin unknown;
- nominality redacted;
- full history.

“Creation Voucher Management confirmed” is provenance/audit information and
should not automatically occupy the same level as owner-facing lifecycle
reports unless a concrete managerial use is identified.

## Acceptance scenarios

No release candidate is valid until these scenarios produce the same facts in
Voucher, alignment, reports, alerts and revocation policy.

### S1 - Verified legacy print, later used and expired

- created 25/09;
- verified HMAC print 25/09;
- cumulative uses > 0;
- first use from UniFi;
- expires;
- later disappears from controller.

Expected: print remains certain with original date/copies; use remains certain;
expired remains in historical reports after disappearance; never appears as
unprinted or revocation candidate.

### S2 - Controller-discovered, no print evidence

- present on UniFi;
- not application-created;
- no verified physical print;
- operator classifies nominality.

Expected: after alignment -> NOT_PRINTED; eligible for normal print/operational
unprinted review according to age, never silently UNKNOWN.

### S3 - PDF generated, not physically printed

Expected: prepared/PDF-created state remains distinct from PRINTED.

### S4 - Printed and unused security review

- last verified print 25/09 15:12;
- cumulative uses = 0;
- still present, not expired;
- threshold 7 days.

Expected: candidate from 02/10 15:12. A later verified reprint restarts the
threshold from that later print.

### S5 - Expired voucher removed by UniFi

Expected: local lifecycle facts remain reportable. Absence from the live
controller does not erase history.

### S6 - Historical legacy row with print evidence but no lifecycle evidence

Expected: PRINTED can be certain; use/expiry may remain unknown. It must not
enter Expired solely because it came from an old backup.

### S7 - Ordinary deletion

Expected: mandatory reason is preserved and prominent in the Deleted report.

### S8 - External deletion

Expected: local fact and date are preserved after typed direct UUID not-found;
no operator reason is invented.

## Release gate impact

The branch remains Draft. No new Setup/UAT artifact should be treated as a
release candidate until:

1. data invariants are implemented and migrated;
2. legacy print reconciliation is guaranteed;
3. report projections are purpose-specific;
4. characterization tests protect existing correct behavior;
5. end-to-end lifecycle fixtures pass across every consumer;
6. exact-head Windows CI is green;
7. real-controller field UAT passes;
8. separate external review is clean.

## Open product decision

One UX decision still needs explicit owner approval:

Should verified legacy history reconciliation become an automatic/guided
upgrade step after the first successful UniFi sync, so operators cannot enter
normal reporting with known legacy history still unmaterialized, or should it
remain a manual maintenance action?

Engineering recommendation: make it a normal guarded upgrade/reconciliation
step, idempotent and visible, with ambiguous/unresolved evidence surfaced rather
than allowing silent data-source divergence.
