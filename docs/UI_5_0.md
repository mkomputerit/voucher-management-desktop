# Voucher Management 5.0 UI design contract

Status: implementation baseline for the 5.0.1 corrective release.

This document records the intended 5.0 operator experience. It is a product
contract, not a description of Tk implementation details.

## Product goal

Voucher Management must look and behave like a finished Windows management
application for non-technical operators, not like a portable networking tool.

The 5.0 visual shell therefore prioritizes:

- a distinct professional identity;
- clear hierarchy, spacing and task grouping;
- a restrained Windows-native light/dark appearance;
- primary actions that are immediately recognizable;
- understandable operational states;
- implementation details hidden from normal workflows.

Terms such as SQLite, WAL, HMAC, checkpoint and integrity-check are engineering
concepts and must not be required knowledge for an operator.

## Primary navigation

The persistent top-level information architecture is:

1. **Home**
2. **Voucher**
3. **Report**
4. **Impostazioni**

The controller is configuration, not the Home page.

## Home

Home answers the operator's immediate questions:

- Is the workstation ready?
- How many vouchers are active?
- How many still need printing?
- What are the primary actions?
- What happened recently?

The controller state is shown discreetly as ready, local/offline or not
connected. API roots and API keys are not displayed on Home.

Recent activity is derived from privacy-safe durable audit facts and must not
expose voucher codes or backup paths.

## Voucher workspace

The Voucher area owns daily creation, selection, document generation, printing
and permitted deletion.

Selection must be visually unambiguous. A checked voucher also receives the
native Treeview selection highlight.

After confirmed physical print submission, the printed vouchers are
automatically deselected.

Reprinting remains a distinct, explicitly confirmed operation based on durable
print audit facts. UI redesign must not bypass the duplicate-print policy.

## Controller settings

Controller configuration lives under Settings and supports:

- saved descriptive profiles;
- profile selection;
- preparing a new controller profile;
- renaming;
- logical removal without deleting historical controller/voucher facts;
- URL configuration;
- volatile API-key entry;
- connection verification;
- understandable connection state.

Removing a profile sets it inactive; historical facts remain durable. Adding the
same controller URL again reactivates the existing historical identity.

The API key is never persisted.

TLS trust rules are unchanged: when Windows does not trust the certificate, the
fingerprint must be shown and explicitly approved before the API key can be
sent. Certificate changes require the same explicit re-verification.

## Settings structure

Settings are separated by operator task:

- **Generali**
- **Controller**
- **PDF / stampa**
- **Retention**
- **Backup**

Backup and restore are a dedicated section. Migration/recovery functions are
available as advanced data tools rather than being mixed into normal settings.

## Backup language

Normal UI speaks in operator terms:

- Backup
- Last backup / result
- Create backup
- Restore backup
- Backup before close

Encryption, SQLite snapshotting, WAL normalization and HMAC identity are
implementation/security guarantees and are not normal operator vocabulary.

## First-run onboarding

The intended fresh-installation flow has eight explicit steps:

1. Welcome
2. Installation identity
3. UniFi controller
4. Connection verification
5. PDF / print configuration
6. Retention
7. Summary
8. Optional local print test

The API key remains memory-only. The connection verification preserves the TLS
fingerprint trust boundary.

The print test is credential-free and local: it does not create a UniFi voucher
and does not enter voucher print history.

Onboarding is crash-safe. An interrupted attempt remains incomplete and is
offered again. When prior 4.x/per-user data exists, the migration decision takes
precedence over ordinary onboarding.

## Existing-data startup choice

When a shared installation detects prior per-user data, the operator must have
four clear choices:

- migrate the prior data;
- restore a Voucher Management backup;
- start a new shared installation while leaving the old data untouched;
- close the application.

Starting fresh is an explicit durable decision. It must not require manually
deleting AppData.

## Retention

Retention uses plain language and a recommended value. The operator is told what
is protected and what may become a candidate after the selected period.

No destructive minimization runs silently; review and selection remain
mandatory.

## Reporting

Report is a first-class workspace. It exposes the existing privacy-safe report
engine with direct access to common views plus controller scope and PDF/CSV
export.

Administrative reports must continue to exclude clear voucher codes except for
the already-defined explicit operational-handoff exception.

## PDF layout

The successful voucher sheet geometry is not redesigned casually. Visual
changes are controlled: identity/logo/text presentation may improve while the
functional A4 voucher format remains stable.

## Windows theme and color

Light/dark follows Windows unless the operator explicitly chooses another
supported theme.

Color is used sparingly for hierarchy and state. Connection state may use a
small green/amber/red signal; the application must not become a colorful web
dashboard.

## Release regression boundary

UI work must not weaken:

- API-key volatility;
- TLS pin verification before credential transmission;
- crash-safe create and print boundaries;
- reprint confirmation;
- automatic deselection after confirmed printing;
- SQLite durability and reporting privacy;
- encrypted backup/restore validation;
- migration precedence;
- shared ProgramData ACLs;
- machine-wide single-instance behavior.
