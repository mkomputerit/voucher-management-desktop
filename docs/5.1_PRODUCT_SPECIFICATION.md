# Voucher Management 5.1 — Product and Engineering Specification

Status: **binding development baseline for the 5.1 release candidate**

Branch: `feature/5.1-reporting-core`

This document is the durable source of truth for the 5.1 product requirements.
It consolidates the approved product decisions, field observations, engineering
reviews and release constraints that previously existed across conversations,
pull-request reviews, changelog entries and implementation notes.

When implementation and this specification disagree, the implementation must be
reviewed. Existing correct behavior must not be removed merely to simplify a
refactor.

## 1. Product purpose

Voucher Management is a Windows desktop application for operating UniFi guest
vouchers while preserving administrative and audit facts that UniFi may no
longer expose after the live voucher disappears.

The product must do two things exceptionally well:

1. **never regress behavior that is already correct and stable**;
2. **provide durable, reliable history and operator workflow where UniFi alone
   is insufficient, without inventing facts that were never observed or
   explicitly classified.**

The intended deployment is **one workstation / one UniFi controller-site
identity** for the normal production installation.

## 2. Non-negotiable engineering principles

### 2.1 No regressions

Before changing an established behavior, characterize it with tests. Refactors
must preserve already-correct behavior unless an approved product requirement
explicitly changes it.

Protected areas include, at minimum:

- official UniFi Network API adapter and pagination;
- verified Site UUID identity;
- TLS certificate validation and explicit SHA-256 pinning;
- API key memory-only handling;
- non-idempotent create guard and uncertain-create recovery;
- physical-print crash boundary and HMAC history;
- backup/restore integrity and rollback;
- ordinary deletion vs security revocation separation;
- typed direct-UUID verification before accepting external disappearance;
- live-only Home semantics;
- shared Windows deployment, ProgramData and ACL behavior;
- report preview-before-save/print;
- operator selections and actions already covered by regression tests.

### 2.2 Positive facts are monotonic

A later incomplete or apparently regressed controller snapshot must never erase
a positive verified fact.

Therefore:

- once physically printed, a voucher never becomes unprinted;
- once used, a voucher never becomes never-used;
- cumulative `authorizedGuestCount` never decreases locally;
- `activatedAt`, once positively known, cannot be erased by a later null;
- positive expiry evidence cannot regress;
- deletion/revocation never removes the retained local history;
- verified legacy HMAC physical-print evidence is equivalent to verified 5.x
  physical-print evidence;
- positive evidence always wins over a weaker/negative classification.

Unknown facts remain unknown until there is positive evidence or an
operator-owned classification explicitly permitted by this specification.

## 3. UniFi contract and controller identity

Voucher Management uses the documented UniFi Network integration API.

The production contract validated against UniFi Network 10.6.106 includes:

- site discovery;
- voucher list with pagination;
- voucher detail by UUID;
- voucher creation;
- single-voucher deletion;
- `createdAt`;
- `name`;
- `code`;
- optional `authorizedGuestLimit`;
- cumulative `authorizedGuestCount`;
- optional `activatedAt`;
- optional `expiresAt`;
- `expired`;
- `timeLimitMinutes`;
- optional data/rate limits.

Product semantics:

- `authorizedGuestCount` is treated as a cumulative count of authorized
  guests observed by Voucher Management;
- any value greater than zero is positive use evidence;
- `activatedAt` is certain first-use/activation evidence;
- validity begins with first activation, not voucher creation;
- a voucher positively reported expired is necessarily considered used;
- there is no verified `lastUsedAt` field in the current consumed contract;
- `last_seen_at` and `last_synced_at` are technical synchronization facts,
  never a substitute for last use.

Controller identity is API root + verified **Site UUID**. Once associated,
Voucher Management must reconnect to the same Site UUID and must not silently
pick another Site at the same URL.

Voucher identity is controller/site + UniFi voucher UUID. Voucher code is not
the primary identity.

## 4. Ownership of data

### 4.1 UniFi-owned, read-only locally

The following come from UniFi and must not be arbitrarily edited locally:

- voucher UUID;
- code;
- name / recipient / description;
- created-at timestamp;
- duration;
- authorized guest limit;
- cumulative authorized guest count;
- activation timestamp;
- expiry timestamp;
- expired state;
- optional data/rate limits.

There is **no second editable local recipient**.

### 4.2 Voucher Management / operator-owned

Local facts may include:

- nominality: Nominale / Non nominale;
- local notes;
- alignment completion;
- creation provenance when positively known;
- physical print facts;
- audit/history;
- ordinary deletion request/reason;
- security-revocation workflow facts;
- synchronization and reconciliation evidence.

Notes are editable only for **one voucher at a time**. Nominality supports
multi-selection.

## 5. Canonical voucher fact model

All user-facing consumers must resolve the same canonical facts instead of
independently interpreting raw stores.

Evidence may physically live in:

- live UniFi objects;
- SQLite vouchers;
- SQLite print jobs and voucher prints;
- HMAC `history.jsonl`;
- legacy audit-event tables;
- operator metadata and voucher events.

But Voucher table, alignment, reports, alerts, ordinary deletion and security
revocation must agree on one deterministic interpretation.

Canonical facts include:

### Identity / controller facts

- controller/site identity;
- UniFi UUID;
- code;
- recipient/name;
- created_at;
- duration_minutes;
- authorized_guest_limit;
- cumulative authorized_guest_count;
- first_used_at;
- expires_at;
- expiry evidence/status;
- presence on controller.

### Local facts

- nominality;
- notes;
- origin/provenance;
- alignment completion.

### Print facts

- PRINTED / NOT_PRINTED / UNKNOWN;
- first verified physical print;
- last verified physical print;
- print jobs;
- physical copies;
- reprints;
- print operators;
- evidence source when needed for audit.

### Deletion/revocation facts

- request date where applicable;
- confirmed outcome date;
- workflow/source;
- mandatory operator reason for application-performed ordinary deletion;
- no invented reason for external deletion;
- operator identity when locally known;
- confirmation source.

## 6. Creation workflow

A controller POST is non-idempotent and must never be automatically repeated
after an uncertain outcome.

Before mutation the application persists a privacy-safe anti-repeat
intent/guard. It must not contain API key, clear voucher code or clear
recipient.

Creation requires a current authoritative UniFi snapshot.

A successful POST remains a confirmed remote creation even if later local
persistence or follow-up listing fails. Confirmed UUIDs and their local
classification require durable recovery.

A stale successful list after POST must not make confirmed UUIDs disappear from
the application model.

New vouchers created by Voucher Management are:

- origin APPLICATION;
- already aligned;
- nominality explicitly chosen by the operator;
- print state NOT_PRINTED until positive physical-print evidence exists.

## 7. Synchronization and disappearance

Home may use only a successful authoritative UniFi snapshot from the current
session.

Local history must outlive controller presence.

A single list omission never proves deletion. External disappearance uses a
conservative sequence:

1. omission becomes suspicious;
2. a subsequent verification performs a direct UUID read;
3. only typed not-found evidence confirms external absence.

A failed/partial snapshot never archives or deletes historical facts.

When a voucher is confirmed absent externally, the archive retains all known
lifecycle, print and operator-owned facts.

## 8. Alignment of controller-discovered / historical vouchers

A voucher found on UniFi but not created by Voucher Management enters as
controller-origin and requires operator alignment when local classifications
are incomplete.

The latest approved product rule is:

- verified HMAC/SQLite physical-print evidence -> **PRINTED**;
- PDF generation alone is not physical print;
- if no positive physical-print evidence exists, after operator alignment the
  voucher is **NOT_PRINTED**;
- nominality is explicitly chosen by the operator;
- a voucher may be Nominale only when the UniFi recipient/name is present;
- controller-owned fields remain read-only;
- notes are optional and single-voucher only.

Historical positive evidence must be reused automatically and may not be
downgraded by the operator.

## 9. PDF and physical printing

PDF generation and physical printing are distinct facts.

- generating a PDF does **not** mean it was physically printed;
- verified Windows print submission/audit creates the authoritative physical
  print fact;
- verified legacy HMAC print evidence also creates the authoritative print fact;
- historical PDF opening is consultation only;
- intentional reprint uses the normal "Stampa selezionati" flow;
- after print or local-recording operations, the affected voucher selection is
  cleared;
- a voucher not yet properly aligned must not become printable through an
  accidental selection-path shortcut.

Voucher PDFs:

- use the approved A4 label layout;
- keep the recipient text inside the cut area;
- do not prefix it with "Destinatario:";
- use the larger configured logo treatment already approved;
- preserve Unicode/font safety checks.

## 10. Ordinary deletion

Ordinary deletion is a correction path for a preparation/operator mistake. It
is not security revocation.

It requires:

- current controller verification/fresh read;
- completed alignment;
- print state NOT_PRINTED;
- no positive physical-print evidence;
- no positive use evidence;
- mandatory operator reason;
- durable audit of the request/reason **before** sending DELETE.

PRINTED, UNKNOWN/non-determinable or non-aligned vouchers cannot use ordinary
delete.

A confirmed deletion keeps the entire local row/history and records the
confirmed outcome. An uncertain remote outcome remains reconcilable and must
not be silently replayed.

## 11. Security review / revocation

Security review is a separate workflow for printed vouchers without positive
use evidence.

There are two distinct operator-configured thresholds:

1. **Creato ma mai stampato** — operational warning, age from UniFi
   `createdAt`;
2. **Stampato ma mai utilizzato** — security review, age from the **latest
   verified physical print**.

A later verified reprint restarts the second threshold.

A positively PRINTED historical voucher for which the print date cannot be
determined enters security review immediately because no safe age calculation
is possible.

Before security DELETE, the candidate is re-read live. The local history,
voucher code and metadata remain preserved after revocation.

## 12. Home workspace

Home is operational and strictly live.

The four KPIs are:

- Da stampare;
- Attivi;
- Utilizzati;
- Scaduti.

They are populated from the current authoritative controller snapshot, not from
SQLite history.

Connection state uses clear green / amber / red semantics.

- green: current authoritative controller state;
- amber: finite retry / reconciliation state;
- red: connection failed / manual reconnect required.

Home also includes:

- recent vouchers with useful space for roughly 10 rows;
- last verified backup timestamp;
- operational warnings for the two configured thresholds;
- a compact Synchronize/Reconnect action;
- no redundant technical controller controls.

A quick synchronization dialog summarizes saved controller configuration and
asks only for the API key; the key remains memory-only.

## 13. Voucher workspace

The Voucher workspace is operator-oriented and must retain the working modern
5.1 design.

Requirements include:

- blue row selection in dark theme and an equivalent visible selection in light
  theme;
- one coherent dynamic voucher action menu;
- the workspace selection drives Allinea, Nominalità and Note actions;
- nominality works for multi-selection;
- notes work only for a single selected voucher;
- archived/expired rows may remain selectable for safe metadata/history
  inspection where applicable, without becoming printable/deletable;
- controller data are read-only;
- no reintroduction of the removed generic "Dati locali" model;
- no local recipient field;
- selections are cleared after completed print/local operations where specified.

## 14. Report architecture

Report reads the durable local SQLite archive and remains usable offline.
Home and Report must not share authority semantics.

### 14.1 Reports for owner/responsible operator

Business reports answer a concrete question and show only useful fields for that
question. Technical fields must not be included merely because they exist.

Expected business-facing views include:

- historical summary;
- used;
- expired;
- printed;
- printed without positive use evidence;
- never printed;
- created-but-not-printed threshold review;
- security review;
- nominal;
- non-nominal;
- unclassified where operationally necessary;
- security revoked;
- deleted from controller.

Examples of useful fields by purpose:

- Expired: recipient, creation, first use, cumulative uses/quota, first/last
  print, copies, duration, expiry;
- Used: recipient, creation, first use, cumulative uses/quota, expiry and useful
  print facts;
- Printed/unused: recipient, creation, first/last print, copies, age from last
  print, live presence;
- Created/not printed: recipient, creation, age, nominality, live presence;
- Security review: recipient, last print, elapsed age/unknown-age reason,
  threshold, cumulative use evidence and live presence;
- Deleted: recipient, deletion date, deletion source/workflow and **reason
  prominently when known**;
- nominality reports: recipient/classification plus lifecycle fields useful to
  the responsible person.

### 14.2 Technical / full audit

Technical data belong in the Full Audit view, not in ordinary manager reports.

Full audit may include:

- UniFi UUID;
- controller identity;
- origin/provenance;
- first import/acquisition;
- last_seen_at;
- last_synced_at;
- controller freshness;
- technical event source;
- print job/operator detail;
- deletion/revocation confirmation source;
- migration/reconciliation evidence.

"Ultima osservazione controller" must mean `last_seen_at`, not
`last_synced_at`. If both are shown in audit they must be correctly labeled.

### 14.3 Report correctness rules

- report categories may overlap where business meaning overlaps;
- nominality is the current explicit classification;
- a negative use report means "no positive use observed", unless a stronger
  terminal fact exists;
- freshness/as-of data must be visible where negative evidence matters;
- positive use/print/expiry facts survive controller disappearance;
- summary is aggregate-only;
- ordinary reports do not expose voucher codes;
- explicit Full Audit may expose codes only through the reviewed explicit
  operator option;
- technical diagnostic categories must not crowd the main owner-facing report
  chooser;
- the guided report selector remains available;
- the owner-facing guide must explicitly expose the existing **Nominal** report
  as the view for vouchers assigned to people;
- the owner-facing guide must explicitly expose **Deleted from controller** as
  the view for preparation-error deletions, keeping it distinct from
  **Security revoked**;
- PDF report generation opens preview first, then allows save/print.

## 15. Legacy history and pre-SQLite backup import

Legacy evidence is security/audit data, not a reason to invent lifecycle facts.

Rules:

- HMAC evidence is resolved only against independently known clear candidate
  codes;
- ambiguous/unresolved rows stay explicit and are never guessed;
- verified legacy physical-print events materialize idempotently into SQLite;
- legacy PDF-generation events prove only PDF generation, not controller
  creation and not physical printing;
- importing a historical legacy row must not mark it expired without positive
  expiry evidence;
- old historical data remain usable even if the voucher is no longer on UniFi;
- old 5.x/4.x backup import remains supported.

### 15.1 Automatic/guided reconciliation — approved

Verified legacy HMAC reconciliation must become a **normal guarded
upgrade/runtime step after the first successful authoritative UniFi sync**,
rather than remaining a hidden manual maintenance prerequisite.

The step must be:

- idempotent;
- visible to the operator;
- automatic/guided rather than silent destructive mutation;
- backed by the existing verified identity/HMAC machinery;
- safe when evidence is ambiguous or unresolved;
- unable to continue into apparently authoritative reporting while known
  resolvable legacy print evidence remains unmaterialized;
- accompanied by clear operator status for unresolved/ambiguous evidence.

This decision is approved and replaces the previously open architecture
question.

## 16. Backup, restore and onboarding

First-run onboarding supports starting clean or restoring an existing backup.

It configures:

- installation identity;
- UniFi controller verification and TLS trust;
- logo/PDF identity;
- explicit "created but never printed" threshold;
- explicit "printed but never used" threshold;
- default backup folder;
- whether to propose backup on close.

Backup behavior:

- verified SQLite-consistent snapshot;
- integrity validation;
- rollback-safe restore;
- password protection optional but selected by default;
- encrypted `.vmbk` when password protection is kept enabled;
- explicit unencrypted ZIP only when the operator disables protection;
- backup-on-close offers create backup / exit without backup / cancel;
- alternate destination for one backup does not overwrite the saved default;
- Home shows the last verified successful backup;
- API root, Site UUID live association and TLS pin are reset after restore;
- the historical controller identity inside SQLite remains history, not live
  trust;
- backup/restore are blocked while an uncertain create outcome is unresolved.

## 17. Security and privacy

- API key exists only in memory for the active operation/session;
- no API key in settings, logs, backups or repository;
- TLS verification is enabled by default;
- self-signed certificates require explicit fingerprint verification/pinning;
- changed pin is blocked before credentials are sent;
- report code exposure is centrally gated;
- CSV output prevents spreadsheet formula execution;
- PDF text is escaped;
- output publication is atomic;
- clear voucher credentials, production PDFs and deployment secrets must never
  be committed;
- current release does not perform destructive privacy minimization that would
  erase required operational/audit facts;
- revoked/deleted voucher credentials remain locally readable as required by
  the current project phase.

## 18. Windows deployment

Target is a professional Windows desktop application.

The final deliverable is a self-contained Setup EXE backed by the reviewed
shared-deployment logic.

Managed deployment:

- program files under Program Files;
- shared data under ProgramData/VoucherManagement;
- explicit ACLs for SYSTEM, Administrators and built-in Users as already
  reviewed;
- machine-wide single instance;
- Start Menu integration;
- safe staged upgrade;
- uninstall preserves data unless explicit data removal is chosen.

Portable build remains a useful pre-release/UAT artifact but is not a substitute
for the final installer gate.

## 19. UI/UX baseline

The visual direction is inspired by the clean UniFi Portal hierarchy without
copying product branding.

Required characteristics:

- professional management-software appearance;
- clear Home / Voucher / Report / Impostazioni navigation;
- light and dark themes;
- green/amber/red connection indicator;
- clear blue selection in dark theme;
- minimal technical clutter for normal operators;
- technical details reserved for Settings/audit/diagnostic surfaces;
- guide-first report discovery;
- clear operator language rather than implementation terminology.

DPI/Windows checks at 125% and 150%, mixed-monitor behavior and keyboard
navigation are release checks.

## 20. Acceptance lifecycle scenarios

The release candidate must produce the same canonical facts across Voucher,
alignment, reports, alerts and revocation.

### S1 — legacy verified print, later used and expired

Expected: print remains certain with original evidence; use remains certain;
expiry remains historical after controller disappearance; never classified as
unprinted/security-unused.

### S2 — controller-discovered, no physical-print evidence

Expected: after operator alignment -> NOT_PRINTED; nominality explicit; eligible
for normal print and created/not-printed review according to age.

### S3 — PDF generated only

Expected: not physically printed. PDF-generation evidence is retained without
creating PRINTED.

### S4 — printed and unused security review

Expected: threshold starts from latest verified physical print. A verified
reprint restarts it.

### S5 — expired voucher disappears from UniFi

Expected: local lifecycle facts remain available in reports.

### S6 — legacy row with verified print but unknown lifecycle

Expected: PRINTED certain; use/expiry may remain unknown. It must not be marked
expired merely because it is old/historical.

### S7 — ordinary deletion

Expected: mandatory reason retained prominently with deletion audit.

### S8 — external deletion

Expected: direct UUID not-found confirmation retained; no operator reason is
invented.

## 21. Confirmed 5.1 golden baseline

The reliability work previously listed in this section has been implemented and
protected by regression/end-to-end tests. It is now part of the **non-regression
baseline** for 5.1.

Field UAT on 2026-10-03 additionally confirmed the following operator-visible
behaviors on the real application:

- the operator was able to complete alignment of all vouchers;
- the two retention/security day-threshold workflows behave as intended;
- report selection and report management are materially improved and usable.

These confirmed behaviors are now release-critical baseline behavior. Future
changes must preserve them unless the product specification is explicitly
changed first.

In particular, do not regress by:

- reintroducing UNKNOWN/"Non determinabile" for controller-discovered vouchers
  after successful operator alignment when no positive print evidence exists;
- breaking batch/single alignment workflows that currently allow the operator
  to complete voucher classification;
- coupling retention thresholds back together or changing their age basis;
- removing or weakening purpose-specific reports, report guidance, preview-first
  behavior, or the separation between **Operativo / titolare** and
  **Audit / diagnostica tecnica**;
- replacing currently working operator workflows while fixing unrelated UI
  defects.

Real-Windows UAT also exposed a common DPI/layout defect in modal windows with
expandable lists: bottom actions could be hidden until the window was enlarged.
The correction must preserve the golden functional baseline above while making
the footer/actions permanently visible at normal initial window size.

## 21A. Global post-operation refresh invariant

This is a binding non-regression rule for every voucher workflow in every menu.

After **any successful operation that changes voucher-related state**, the
application must automatically reconcile the visible UI with the new durable
state. The operator must never need to press **Sincronizza** merely to make a
completed local operation visible.

The rule applies, including but not limited to:

- alignment;
- nominality;
- local notes;
- print / reprint;
- ordinary deletion;
- security revocation;
- controller-discovered voucher handling;
- legacy reconciliation that materializes voucher facts;
- retention/security actions;
- voucher creation;
- any future voucher mutation added to Home, Voucher, Report, Settings or
  maintenance workflows.

On successful completion the application must, as applicable:

1. clear the global voucher selection model;
2. remove the blue selection/highlight from both Voucher and Home;
3. refresh the Voucher workspace from current durable facts;
4. refresh Home presentation that depends on local voucher state;
5. recalculate the two Home retention/security counters;
6. refresh report summaries / data-quality indicators affected by the change;
7. refresh any open operational dialog that remains valid after the action;
8. update controller-workspace/status indicators when their displayed state is
   affected.

The refresh must use the **appropriate authority**:

- for local-only facts (alignment, nominality, notes, print audit, local
  reconciliation), refresh from SQLite/current in-memory controller snapshot;
  do **not** require or invent a new UniFi synchronization;
- for confirmed remote mutations (create, delete, revoke), update from the
  authoritative operation result and the reviewed remote-verification workflow;
  perform an additional controller fetch only when the specific workflow
  requires it for correctness.

Failure semantics:

- do not clear the selection or present refreshed success state when the
  operation failed;
- if the remote outcome is uncertain, preserve the reviewed uncertainty/recovery
  workflow instead of pretending the operation completed;
- a refresh failure after a successfully committed operation must be reported as
  a UI refresh problem, not as failure of the already-completed mutation.

This invariant exists to prevent stale UI from making the operator believe that
an operation did not occur, and to prevent selections made for one operation
from accidentally carrying into the next one.

## 22. Release gate

No merge/tag/release until all of the following are complete:

1. canonical data invariants implemented and migrated;
2. approved automatic/guided legacy reconciliation implemented;
3. purpose-specific report projections implemented;
4. regression/characterization tests protect prior correct behavior;
5. end-to-end lifecycle scenarios pass across all consumers;
6. exact-head Windows CI is green;
7. real UniFi controller field UAT passes;
8. separate external-review pass has no blocker/high findings;
9. final portable/Setup candidate is tested on Windows;
10. only then merge, tag and publish 5.1.0.

The PR remains Draft until these gates are satisfied.
